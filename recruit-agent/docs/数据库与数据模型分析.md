# RecruitOS 数据库与数据模型分析

| 项目 | 内容 |
|------|------|
| 文档版本 | V1.0 |
| 编制日期 | 2026-08-05 |
| 分析对象 | `backend/prisma/schema.prisma` + `backend/src/seed.ts` |
| 数据库引擎 | SQLite（开发态，Prisma ORM） |

---

## 1. 分析目标与范围

本文档聚焦当前 RecruitOS（含 HR Agent 集成）的数据库与数据模型设计质量评估，覆盖：

- 领域建模完整性（是否覆盖招聘全流程与二期能力）
- 关系建模合理性（主外键、约束、版本化、可追溯性）
- 可扩展性与性能风险（索引、字段形态、统计口径）
- 数据安全与治理能力（脱敏、软删除、审计留痕）
- 后续演进建议（短中期可落地改进）

---

## 2. 总体结论（Executive Summary）

当前模型整体属于 **“业务优先、可运行闭环、便于快速迭代”** 的设计：

- 优势：流程主线清晰、实体边界基本正确、Agent 风险控制模型较完整；
- 代价：为快速交付引入较多 `String/JSON` 字段，规范化与索引建设不足；
- 结论：当前适合中小规模本地/测试场景，若走生产规模，需要补齐索引、约束、枚举化与数据治理。

建议优先级：

1. **P0**：关键查询索引 + 状态枚举收敛 + 行级权限过滤落地  
2. **P1**：高频 JSON 字段结构化拆分 + 审计/事件归档策略  
3. **P2**：面向 PostgreSQL 的迁移准备（约束、分区、全文检索）

---

## 3. 数据模型结构概览

## 3.1 领域分层

当前 schema 可分为 5 组：

1. **组织与权限域**：`Organization`、`User`、`Dictionary`、`Template`
2. **招聘主流程域**：`RecruitRequest`、`Job`、`Candidate`、`Application`、`ProcessEvent`
3. **面试录用入职域**：`Interview`、`InterviewEvaluation`、`Offer`、`Onboarding`
4. **运营与协同域**：`Todo`、`Activity`、`MessageLog`、`SlaRule`、`Alert*`、`WarmTask`
5. **Agent 与二期扩展域**：`JobStandard`、`EvalModel`、`FlowTemplate`、`Channel*`、`SecureLink`、`Agent*`、`BusinessEvent`、`SemanticDict`、`HireQualityRecord`

## 3.2 主流程关系（核心链路）

`RecruitRequest -> Job -> Application <- Candidate`

并沿 `Application` 扩展：

- `Application -> Interview -> InterviewEvaluation`
- `Application -> Offer -> Onboarding`
- `Application -> ProcessEvent`（流程时间轴）

该建模方式符合“**状态挂应聘记录，不挂候选人主档**”原则，支持同一候选人多岗位并行应聘。

---

## 4. 设计亮点（优点）

## 4.1 流程边界清晰

- 候选人主档（`Candidate`）与流程实例（`Application`）分离；
- 面试评价使用 `InterviewEvaluation@@unique([interviewId, interviewerId])` 避免同轮重复评价；
- Offer 使用 `version + isActive` 实现版本化，满足审批重提需求。

## 4.2 风险控制可追溯

- `AgentAction` 内置 `riskLevel/status/idempotencyKey/confirmUserId`；
- 高风险动作支持“待确认 -> 执行”闭环，且可审计；
- `BusinessEvent` + `EventSubscription` 为事件化扩展预留接口。

## 4.3 二期能力可配置化基础较好

- `FlowTemplate/FlowNode` 支持流程节点配置与 SLA；
- `JobStandard/EvalModel` 支持岗位标准与评价模型版本化；
- `Channel/JobChannelPublish` 支持多渠道发布追踪。

## 4.4 可演示数据完备

- `seed.ts` 覆盖淘汰、入库、推进中的三类候选样本；
- 同时初始化语义字典、流程模板、门户 token，便于联调验收。

---

## 5. 关键问题与风险点

## 5.1 枚举字段大量使用 `String`（约束弱）

现状：大量状态/类型字段依赖注释约定（如 `Application.status`、`Offer.status`、`AgentAction.status`）。

风险：

- 易出现脏值（拼写、大小写、历史值不一致）；
- 报表统计口径不稳，跨版本迁移成本上升。

建议：分阶段引入 Prisma enum（或字典映射层），先从高频状态字段开始。

## 5.2 JSON/文本字段较多（查询与治理弱）

示例：

- `Candidate.parsedResume`、`InterviewEvaluation.scores`
- `JobStandard.skills`、`EvalModel.dimensions`
- `Interview.slotOptions`、`Onboarding.materials`

风险：

- 难以建立高效过滤索引；
- 数据质量校验与变更治理困难；
- 复杂报表需要应用层反序列化，CPU 消耗增加。

建议：把高频过滤字段拆成结构化列，低频长文本保留 JSON。

## 5.3 索引建设不足

除主键/少量 unique 外，业务高频查询列缺少显式索引（如 `Application.status`、`jobId`、`Candidate.phone/email`、`ProcessEvent.createdAt`）。

风险：

- 数据量上升后列表与报表性能显著下降；
- SQLite 到 PostgreSQL 迁移后如果不补索引，慢查询会集中爆发。

建议：补齐“状态、时间、外键、唯一识别”四类索引（见第 7 章）。

## 5.4 权限模型落地不完整

`User.dataScope` 已建模，但当前文档与实现说明显示“行级数据过滤尚未全面落地”。

风险：多组织、多部门场景下存在越权查看风险。

建议：将 dataScope 过滤策略内聚到统一查询构造器，避免路由散落实现。

## 5.5 软删除策略不统一

- `Candidate` 有 `deleted/anonymized`；
- 多数实体仍为硬删（seed 全量 deleteMany）。

风险：历史追溯与合规留存策略不一致，长期可能产生审计争议。

建议：明确“业务数据软删 + 日志事件只追加”的分层策略。

---

## 6. 与 HR Agent 集成的模型评估

## 6.1 现有适配能力

已具备较好的 Agent 集成落点：

- 输入侧：`/api/agent/query` 可按对象读取上下文；
- 生成侧：`AgentDraft` 存草稿，避免直接改正式数据；
- 动作侧：`AgentAction` 支持幂等与人工确认；
- 事件侧：`BusinessEvent` 支持后续 webhook/订阅扩展。

## 6.2 主要缺口

- 缺少调用追踪链路字段（如 traceId/requestId），跨 RecruitOS 与 HR Agent 排障成本高；
- 缺少“模型版本/提示词版本”落库字段，难以做生成质量回溯；
- `SemanticDict` 可用但尚未形成严格数据契约。

建议：为 `AgentDraft` / `AgentAction` 增加 `modelName/promptVersion/traceId`。

## 7. 优化建议（分阶段）

## 7.1 P0（1~2 周）

1. **补索引（优先）**
   - `Application(jobId, status, updatedAt)`
   - `Application(candidateId, status)`
   - `ProcessEvent(applicationId, createdAt)`
   - `Interview(applicationId, startTime, status)`
   - `Offer(applicationId, isActive, status)`
   - `Candidate(phone)`、`Candidate(email)`（可空唯一策略视业务决定）
   - `AgentAction(status, createdAt)`、`AgentDraft(type, status, createdAt)`

2. **状态值治理**
   - 建立统一状态常量映射（前后端共享）；
   - 对高频状态字段增加输入校验（zod + service 层）。

3. **权限收敛**
   - 落地统一 dataScope 过滤器（ALL/DEPT/SELF）。

## 7.2 P1（2~4 周）

1. **JSON 热字段结构化**
   - 把 `Candidate.parsedResume` 中高频检索项（技能、年限、学历）拆列；
   - 将 `InterviewEvaluation.scores` 拆分为结构化评分列或衍生评分表。

2. **可观测性补强**
   - 增加 `traceId` 贯穿 RecruitOS <-> HR Agent；
   - 增加 `modelName/promptVersion` 记录生成来源。

3. **数据治理策略**
   - 定义软删/归档/匿名化规则与保留周期；
   - 为审计与事件日志增加归档计划。

## 7.3 P2（1~2 月）

1. **迁移 PostgreSQL 方案**
   - 枚举、JSONB、GIN/BTREE 索引、分区策略；
   - 报表与全文检索能力增强。

2. **模型契约治理**
   - 统一 `SemanticDict` 与 API schema 版本；
   - 建立跨服务数据字典与兼容策略。

---

## 8. 建议的目标模型能力清单（生产化）

- 强约束：关键状态枚举化、关键关系外键完整、唯一约束清晰；
- 高性能：高频列表与报表索引完备、统计路径可控；
- 高治理：软删/匿名化/审计闭环一致；
- 可追踪：跨 RecruitOS/HR Agent 的调用链可回放；
- 可扩展：流程模板、评价模型、渠道映射支持增量演进。

---

## 9. 结语

当前数据库与数据模型设计已经具备“可运行、可演示、可扩展”的良好基础。  
若进入更高并发和更严格治理场景，建议按本文优先级推进索引、约束和数据治理改造，以降低未来迁移成本并提升系统稳定性。
